## Executive verdict

The application compiles, typechecks, tests, and builds, and the production
login surface is reachable with the expected baseline headers. It is not ready
for pilot certification. The primary blockers are destructive deletion of
append-only scan events, an unverified tenant-query inventory, missing browser
coverage and page scores, a broken production health endpoint, test-process
leaks hidden by `--forceExit`, and broad RTL and type-hygiene debt.

## Findings

### P0

None confirmed during this static pass.

### P1 — Critical/high

1. **Scan history can be permanently destroyed.**
   `apps/client-dashboard/src/app/api/danger/purge-scans/route.ts` calls
   `prisma.scanLog.deleteMany`. `ScanLog` contains the access decision,
   `scanUuid`, gate, QR, operator, and audit trail. This contradicts the
   append-only access-event contract. The route is authenticated, permission
   checked, explicitly confirmed, tenant constrained through `gate`, and writes
   an `AuditLog`, but the deletion still removes primary access evidence.

2. **Tenant isolation is not certifiable from the current static scan.**
   The deterministic tenant scanner reported 73 possible unscoped Prisma
   operations across analytics, contacts, CRM, gates, residents, scans,
   workspace, webhooks, and danger routes. These are candidates, not 73
   confirmed vulnerabilities; each must be manually classified against model
   ownership, relation scoping, request-local tenant context, and documented
   privileged exceptions.

3. **AI conversation content is persisted in `localStorage`.**
   `apps/client-dashboard/src/components/dashboard/ai-assistant.tsx` stores full
   assistant messages. Prompts can contain resident, unit, QR, or scan context.
   This is not token storage, but it creates cross-session privacy and shared
   device exposure without a retention or sensitivity boundary.

4. **Security certification remains incomplete.**
   The active `audit_remediation_2026` plan still has open credential-rotation
   evidence and all Phase 4 API-certification gates.

### P2 — Medium

1. `/health` is configured in `vercel.json` but has no matching API route and
   returns 404 in production.
2. Tests require `jest --forceExit`, indicating unresolved open handles.
   One QR validation suite is skipped; the focused run reported 25 skipped
   tests overall.
3. Lint passes with 282 warnings, including extensive explicit `any`, unused
   code, and empty blocks.
4. Only 86 of 123 API route files contain a recognizable Zod validation
   pattern. Some exceptions are input-free GET routes or webhook/auth handlers,
   but mutating and path-parameter routes require manual classification.
5. Only 12 API routes contain a recognizable rate-limit helper. Abuse-sensitive
   routes must be checked individually rather than assuming global coverage.
6. Static RTL review found 248 physical-direction utility occurrences versus
   34 logical-direction occurrences. Several high-use screens use unqualified
   `ml`, `mr`, `pl`, `pr`, `left`, and `right` classes.
7. CSP permits `'unsafe-inline'` and `'unsafe-eval'` for scripts. This is a
   hardening gap even though frame, object, base, form, HSTS, referrer, and
   permissions policies are present.
8. `ApiKey` revocation performs a hard delete. The model has no `deletedAt` or
   `revokedAt`, so revocation history is not retained in the primary record.

### P3 — Low

1. Next.js reports that `middleware.ts` should migrate to the `proxy` convention.
2. Prisma is imported through a CommonJS wildcard export that adds runtime
   compatibility code under Turbopack.
3. The route inventory does not exactly match the build manifest and needs a
   parity assertion.
4. Local environment readiness cannot be proven from the invoking shell; the
   deterministic helper did not load `.env.local`. No secret values were read
   or recorded.
